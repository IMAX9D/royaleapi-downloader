# 架构与稳定性

## 浏览器和指纹

当前支持五种 Fetcher。SessionCurl 模式把列表和回放分流：

1. Patchright 启动持久 Chromium profile，在浏览器上下文内执行 `fetch`。浏览器负责 JavaScript、Cookie 和浏览器环境；不同代理分别使用 profile。
2. SessionCurl 使用 curl_cffi 的 AsyncSession；`impersonate` 选择 TLS/HTTP2 浏览器特征，每条代理绑定独立 Cookie 和连接池。
3. User-Agent 是独立配置项。其默认值写有 Chrome/124，而 `impersonate="chrome"` 是库的通用目标，两者不保证对应相同版本。TLS 模拟不能等同于完整浏览器环境。
4. 网站登录状态与浏览器校验状态需要分别维护。旧运维路径包含外部 watchdog 和会话轮换，但一般 CLI 与固定赛季运行不会自动启用它。

## 队列与数据完整性

SQLite 保存 pending / inflight / done / dead / skipped。数据库操作在单线程执行器中串行执行，内存队列有容量限制；重启会恢复 inflight。

列表派生的详情使用 `battle:<tag>` 去重，保存双方卡组与页面来源。回放通过格式、坐标、时间等校验后写入临时文件，flush/fsync 后原子替换；完成状态与索引待发布记录通过事务衔接。重启会补发 index outbox。

名单批次冻结名单哈希、赛季边界和选择条件，避免重跑时混入另一批数据。普通采集与需外部冻结 native contract 的 authoritative 模式分开。

## 限速与资源控制

- 每条线路令牌桶、随机抖动、HTTP 429/403 冷却与网络错误退避。
- 小批量领取任务，回放积压达到高水位后暂停列表发现。
- 可用内存低于暂停阈值时限制新列表任务；高于恢复阈值后恢复。
- 运行锁防止多个采集进程同时使用同一数据库或输出目录。
- 状态文件带更新时间；只读状态会标识陈旧心跳。

## 已知限制（本次发布未声称修复）

| 问题 | 影响 | 当前处理 |
| --- | --- | --- |
| Patchright 的页面内 `fetch` 未设置 AbortController，外层 evaluate 也无显式截止时间 | 浏览器或响应挂起时，列表 worker 可能长期占用 | 监控吞吐与任务变化；需要补齐请求截止时间 |
| SessionCurl 仅初始化时读 Cookie 文件 | 更换会话文件不会自动更新正在运行的连接池 | 刷新有效会话后正常停止并重启同一批次 |
| 重试耗尽进入 dead；重启只恢复 inflight | 某些列表失败会截断后续历史链 | 查看 dead 状态和错误，不能把队列耗尽等同于完整采集 |
| 队列耗尽可进入 completed，即使存在 dead | 完成状态不代表零漏采 | 同时检查任务计数与预期范围 |
| 固定赛季 CLI 未接旧 supervisor/watchdog | 不能依赖旧后台服务自动修复该批次 | 用同一批次参数查询状态并人工恢复 |
| 未完成发布版多日真实网络测试 | 无法保证无人值守运行时长 | 离线测试通过后先小批次验证 |

原代码中的历史成功批次不等于新快照已经完成长期网络验收。发布整理保留采集逻辑，不自动启动代理、登录或下载。

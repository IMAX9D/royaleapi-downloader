# 架构与稳定性

## 浏览器与 HTTP 分工

SessionCurl 使用 Patchright / Chromium 的持久 profile 获取列表，使用 curl_cffi 连接池获取回放。每个代理入口映射自己的会话文件；同一实际出口的多个入口应配置相同速率组。

Chromium 完成首页初始化后转到同源轻量页面，再发起列表请求，减少广告、媒体和计时器的内存占用。初始化并发最多两个，页面请求有 AbortController 和外层等待截止时间；低内存时暂停新增列表任务。

curl_cffi 的 `impersonate` 模拟 TLS/HTTP 特征，不等于完整浏览器环境。会话文件可以记录 `http_impersonate` 和 `http_user_agent`；客户端检测文件变化后更新 Cookie 与传输参数。Firefox 的站点验证 Cookie 不直接移植到 Chromium，列表浏览器保留自己的验证状态。

## 队列与数据完整性

SQLite 保存 pending / inflight / done / dead / skipped；数据库操作在单线程执行器中串行执行。内存任务队列有界，重启恢复 inflight。首页、历史页和重叠窗口公平领取，避免首页刷新持续占用历史回填预算。

历史游标保留毫秒精度。首个游标允许有限的服务器时钟偏差，之后必须严格递减；只接受同站、同玩家的历史链接，优先识别向后翻页方向。时间范围和对局筛选独立执行。

详情按 `battle_tag` 去重。列表元数据与回放合并，解析和筛选通过后先写临时文件，再 flush/fsync、原子替换；完成状态与索引待发布记录通过事务衔接，重启补发 index outbox。

持续高手池模式要求至少一方在已核验玩家池内，并满足开始时间、单场 1v1 和完整卡组等条件。冻结玩家池后停止资格扩容，现有玩家的历史回填与新对局刷新继续运行。

## 限速与会话维护

- 每个实际出口共享令牌桶；同组会话公平轮转，不增加该组总预算。
- 全局回放门控不重复添加节点已有的随机等待。
- HTTP 429、403、网络错误分别计数和退避；重启保留计数与尚未到期的冷却。
- 回放积压达到高水位暂停列表发现，下降到低水位后恢复。
- 可选的 SessionMaintenance 由回放认证失败触发，最多同时运行两个恢复浏览器；重用已有登录态，并通过真实回放 HTTP 请求检查结果。
- 恢复流程有截止时间、失败退避和进程清理；成功登录不会清除已有或新发生的 429 等待。人工登录或验证需求显示在面板上。
- 持续采集入口的旧动态线路管理和外部 supervisor 默认不启用。

## 运行边界

离线测试不证明站点实时可用性。浏览器能打开首页，不代表登录有效或真实回放请求成功；短窗口下载速率也不能证明全天产量。

浏览器恢复不保证通过所有站点挑战。登录过期、需要人工验证、代理服务退出或磁盘不足都可能需要介入。更换出口不是额外的账号配额，访问仍须遵守来源站点规则。

部分通用 CLI 任务重试耗尽后进入 dead，需要人工检查；持续采集对部分临时失败采用较长退避。队列暂时没有任务、页面返回 404 或本机探测失败，均不能证明历史数据已经完整采集或节点永久不可用。

历史 authoritative/native contract 工具和 Mihomo 运维模块仍依赖使用者的外部环境。旧动态线路模块保留原来的端口范围约定，不作为新环境的默认启动方式。多日真实网络稳定性及连续 24 小时 30 万场目标尚未完成验收。
